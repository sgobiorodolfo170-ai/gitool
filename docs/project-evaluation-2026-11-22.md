# Gitool 项目综合评估报告

**评估日期**: 2026-11-22  
**项目版本**: v0.11.1  
**技术栈**: Electron + Vite + React + TypeScript  
**项目类型**: Windows Git 仓库工作台（桌面应用）  
**评估方式**: 纯静态只读分析（源码、配置、架构评审文档）

---

## 一、执行摘要

### 1.1 总体判定

| 维度 | 评分 | 判定 | 核心依据 |
|------|------|------|----------|
| **架构分层** | ⚠️ 部分成立 | 约定俗成的目录分层，非可执行的分层架构 | 主进程 `services → storage` 二分基本成立，渲染层无数据访问边界（14 文件 53 处桥直调） |
| **安全性** | ⚠️ 基线扎实、链路失守 | Electron 安全基线达标，但更新链与凭据外泄存在风险 | 窗口隔离全开，但更新无签名校验、URL 允许内嵌凭据 |
| **工程化** | ⚠️ 门槛口径与风险区错位 | 测试覆盖集中在纯函数层，服务层与组件层几乎零覆盖 | 21 个测试中 15 个在纯函数 + storage，services 4,946 行零测试 |
| **可维护性** | ⚠️ 单文件职责过重，存在重复 | 3 个超 500 行单文件，6 处实体构造重复 | `git.ts` 991 行、`providers.ts` 753 行、`App.tsx` 634 行 |

**一句话结论**: 项目在 Electron 安全基线（`contextIsolation`、`sandbox` 等）上表现扎实，但**架构分层停留在"约定"而非"机制"**——渲染层绕过 hooks 直连 IPC、IPC 承载领域编排、类型安全依赖断言而非校验。最紧迫的 3 件事：**掐断更新链 RCE 路径、凭据落盘止血、渲染层立边界**。

## 三、架构评估核心发现

### 3.1 分层判定（22 条问题）

| 边界 | 判定 | 证据 |
|------|------|------|
| `services → storage` 单向 | ✅ 成立 | SQL 仅出现在 `storage/*`，无反向领域依赖 |
| `storage` 表级所有权 | ⚠️ 局部破防 | `accounts.ts` 写 `remote_repository_cache`，`workspaces.ts` 读 `projects` |
| `ipc.ts` 作为纯适配层 | ❌ 不成立 | 承载领域编排、跨表反查、写操作日志（417-477 行） |
| **Renderer → hook → bridge** | ❌ **不成立** | **14 文件 53 处直调 bridge**，6 个领域无 hook 层 |
| 渲染层不含业务规则 | ❌ 不成立 | 实体字面量 6 处、工作区规则双份、AI prompt 在展示组件 |
| 通道契约单一来源 | ❌ 不成立 | 三处硬编码，2 个死通道 |
| **分层可执行性** | ❌ **不成立** | 无 `dependency-cruiser`/ESLint 分层规则，越界无自动拦截 |

**根因**: 渲染层没有数据访问边界——组件与 hook 平权直连 IPC，是"分层不成立"的唯一根因。

### 3.2 安全评估（18 条问题）

| 检查项 | 判定 | 关键证据 |
|--------|------|----------|
| `contextIsolation` / `sandbox` / `webSecurity` | ✅ 全开 | `index.ts:93-99` |
| preload 暴露面 | ✅ 基本达标 | 80 个显式方法，无 `ipcRenderer`/`fs`/`shell` 直通 |
| **IPC 入参校验** | ⚠️ 部分达标 | 78 个 handler 仅 30 个走 zod，**33 个有入参通道未走 schema** |
| 命令执行（Git 域） | ✅ 正确 | `execFile` + 数组 + `--`/`: (literal)` |
| 命令执行（非 Git） | ⚠️ 3 个风险面 | `updater:install` 的 `cmd /c start`、任务 `shell:true`、UAC 安装无哈希 |
| **凭据外泄通道** | ❌ **未达标** | URL 允许内嵌 `user:token@`，Git 输出未脱敏落库/导出 CSV |
| **更新链完整性** | ❌ **未达标** | 无摘要/签名校验，分发权在第三方个人 GitHub 账号 |
| CSP 与权限策略 | ⚠️ 部分达标 | 生产 CSP 最小化，但缺 `frame-ancestors`、无 `setPermissionRequestHandler` |

**最严重问题（P1）**: 更新链无签名校验——应用从第三方个人账号拉取 release 资产并执行，一旦账号被接管即全量用户 RCE。

### 3.3 测试覆盖（12 条问题）

| 层级 | 测试文件数 | 覆盖率 | 问题 |
|------|-----------|--------|------|
| 纯函数 + storage | 15 | 95/85/90/95 | 白名单 19 文件，**"达标"是子集达标** |
| `services`（4,946 行） | 0 | **0%** | `git.ts` 991 行、`providers.ts` 753 行零测试 |
| `src/components`（5,758 行） | 0 | **0%** | 组件层无回归保护 |
| `src/hooks`（1,872 行） | 1 | 极低 | 仅 `useAsyncData.test.ts` 一个文件 |

**错位**: 覆盖率门槛（95/85/90/95）只对 19 个白名单文件生效，风险最高的 Git 命令拼装、provider HTTP、任务进程生命周期全部无保护。

### 5.2 第 1 批详细计划（最紧迫）

#### 1A. 掐断更新链最短 RCE 路径（P-03、P-04）
- **动作**: `updater:install` 去掉 `cmd /c start` 改为直接 `spawn(exe)`，补 GitHub `digest` 摘要校验 + 代码签名
- **成本**: S（去 cmd）+ M（证书流程）
- **验收**: 单测 `installUpdate("...\\x&calc.exe")` 抛"不受信任"；`Get-AuthenticodeSignature` 校验签名

#### 1B. 凭据落盘止血（P-05、P-06）
- **动作**: 入口拒绝 `https://user:token@host` 形式 URL，`redactSecrets` 覆盖 git 输出/操作日志/CSV，`git clone -c` 改为 `GIT_CONFIG_*` 环境变量注入
- **成本**: S
- **验收**: 单测 `redactSecrets("https://u:tok@h/x")` → `https://***@h/x`；e2e 克隆后 `git config --get credential.helper` 为空

#### 1C. 渲染层立边界第一刀（P-01、P-02、P-17、P-31）
- **动作**: 先做 `shared/` 实体工厂（`createProject`/`createTaskProfile`），再按 Git 域切片把 19 处桥直调收进 `useGitPanel`，配 ESLint `no-restricted-imports`
- **成本**: M（纯函数 + 测试，风险低）
- **验收**: 投影测试绿（工厂产物全部通过 schema）；`bridge.*` 在 `src/components` 从 53 → ≤34

### 5.3 若只做 3 件事

1. **掐断更新链 RCE 路径**（P-03、P-04）—— 唯一"不需要攻破渲染层"即可全量用户 RCE 的路径
2. **凭据落盘止血**（P-05、P-06）—— 令牌会进 `.git/config`、SQLite、CSV，与 README 承诺直接矛盾
3. **渲染层立边界 + 实体单点**（P-01、P-02）—— 唯一会**静默写坏数据**的问题

> 若资源只够做一天，做 **1A 的前半（去 cmd）+ 1B**。
