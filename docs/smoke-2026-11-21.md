## 2. 环境与执行方式

### 2.1 编译到临时目录（避免 TS 运行时）

仓库 `tsconfig.electron.json` 是 `noEmit + module ESNext`，直接 `--outDir` 无法产出可 `require` 的 CJS；因此在 `%TEMP%` 下生成临时 tsconfig（继承仓库配置，`module=commonjs`、`noEmit=false`、`rootDir=D:/github/gitool`、排除 `*.test.ts`），编译产物落在 `%TEMP%\gitool-smoke\dist\electron\...` 与 `dist\shared\...`。

```powershell
$t = "$env:TEMP\gitool-smoke"
npx tsc -p "$t\tsconfig.smoke.json"        # 退出码 0，无错误
node "$t\smoke.cjs"                        # 冒烟入口
```

`NODE_PATH=D:\github\gitool\node_modules`（dist 在 %TEMP%，第三方包仍从仓库 `node_modules` 解析）。

## 4. 断言与判定口径

- 正向步：要求 handler 正常返回 **且** 对返回值做业务断言（分支名、diff 内容、恢复文件存在、任务终态与 stdout 内容等）；异步终态（子进程退出、运行记录落库）用最长 8 s 的短轮询，避免把「进程还没退出」误判成失败。
- 反向步：要求 handler **抛错**、错误对象有名称/错误码/非空中文文案，并断言关键文案片段；同时用 `projects:load` 复核数据库未被污染。
- 所有耗时为主进程 handler 内部真实耗时（不含脚本开销）。

## 6. A-11 误伤评估

| 观察 | 证据 | 判断 |
| --- | --- | --- |
| 正常导入链路不被拦截 | 步骤 2→3→4→6→7→10→12→18 全 PASS（位于 `%TEMP%`，同时在 `home` 根内） | 无误伤 |
| 未登记的外部项目被拒 | 步骤 62：`D:\github\gitool` → `路径不在允许范围内：项目路径` | 设计预期（白名单外） |
| 用户经对话框选定父目录后放行 | 步骤 63→64：选择 `D:\github` 后同一路径 inspect 成功 | 说明「会话选择根」有效，**不是死锁式误伤** |

| 系统目录/盘符根拒绝 | 步骤 53、55、56 | 符合安全目标 |

**结论：本轮没有观察到 A-11 误伤。** 唯一需要注意的是：白名单以 `homedir()` 为默认根，因此非主目录盘符（如 `D:\`）上的项目必须经「选择目录」进入会话根后才能访问；从 UI 主流程看这是可达的，但从 API 直连角度看属于预期限制。

- **现象**：仓库只有一处「未暂存修改」时，`git:changedFiles` 返回 `[]`；`projects:snapshot` 同时报告 `status=dirty / 1 个文件未提交`。步骤 16、28 两次复现。
- **影响**：渲染层 `src/components/git/ChangesTab.tsx:77` 用 `bridge.listChangedFiles(projectPath)` 渲染变更列表；列表为空时显示「暂无变更」。用户看不到未暂存文件，无法在 UI 里暂存/取消暂存/查看 diff，单文件修改时提交链路被卡住。属于**静默数据丢失**，不是报错。
- **根因**：`electron/main/services/git/core.ts:160` 的 `runGit()` 对 stdout 调用 `.trim()`；`git status --porcelain=v1 -z` 的第一条记录以状态位空格开头（未暂存），trim 会吃掉这个前导空格：

```text
原始 stdout            " M README.md\u0000"   ← 解析器 segment[2] === " " 成立
runGit 返回（trim 后） "M README.md\u0000"    ← segment[2] === "R"，被 gitParsing.ts:170 丢弃
```

- **最小复现（真实代码路径，已实测）**：

```js
// git 原始输出
execFileSync("git", ["-C", repo, "status", "--porcelain=v1", "-z"])
// => " M README.md\u0000"

parseStatusPorcelainZ(" M README.md\u0000")  // => [{status:" M", path:"README.md", staged:false}]
parseStatusPorcelainZ("M README.md\u0000")   // => []
```

- **为何单测没拦住**：仓库内只有 `ipc/coverage.test.ts` 对 `git:changedFiles` 做接线检查；`gitParsing` 单测直接喂原始字符串（带前导空格），不经过 `runGit` 的 trim，因此覆盖不到该路径。
- **建议修法（未实施，需授权改业务代码）**：`runGit` 只对面向展示的输出 trim，`-z`/`--numstat` 这类结构化输出改走 `runGitProcessRaw`（不 trim）；或对 `status --porcelain` 单独使用不 trim 的出口。修复后补一条「单文件未暂存修改」的集成级断言。

### P1-2 `backups:create` / `backups:restore` 未接入 A-11 路径白名单（安全覆盖缺口）——✅ 已关闭（2026-11-21 修复后复验，见 §8）

- **现象**：其它路径类通道统一走 `assertPathAllowed` / `requireAllowedProjectPath`，但 `electron/main/ipc.ts:531`、`:534` 的备份两通道只做 schema 校验，直接把 `sourcePath` / `targetDirectory` / `archivePath` 交给服务层。
- **运行证据（安全探针，未执行真实 tar）**：
  - `backups:create({sourcePath:"C:\\Windows\\System32", targetDirectory:"不存在的目录"})` → 错误是 `备份目录不存在或不可写`，说明**源目录已通过 `assertDirectory` 被接受**（`backups.ts:40` 在路径策略之前）；
  - `backups:restore({targetDirectory:"C:\\Windows\\System32"})` → 错误是 `恢复目标目录不是空的，请选择空目录`，说明**系统目录已通过可写性与空目录检查**（`backups.ts:95`）。
- **影响**：若渲染层被攻破，可让主进程把任意可读目录（含系统目录/用户敏感目录）打包到任意可写位置（信息外泄），或把恶意压缩包解到任意空目录（路径穿越风险由 tar 侧承担）。与 A-11「路径白名单」目标不一致。
- **建议**：给备份通道补 `requireAllowedProjectPath`（源）与 `exportPathRoots` 语义（目标/压缩包），并为两通道加白名单接线测试。

### P2-1 超长标签名被拒，但错误文案指向「字符集」而非「长度」——✅ 已关闭（2026-11-21 修复后复验，见 §8）

- **现象**：`git:createTag({name:"a"×500})` 被拒，错误原文 `标签名只能包含字母、数字、点、下划线、斜杠和连字符`。
- **根因**：schema（`schemas.ts` 的 `createTagInputSchema` 用 `requiredString`，上限 4096）放行 500 字符；拦截发生在 `services/gitParsing.ts:22` 的 `isValidRefName`（`length > 255` 与字符集不匹配共用同一返回 `false`），而 `services/git/tags.ts` 只抛字符集文案。
- **影响**：用户按提示修改命名仍会被拒（实际是长度超限），可诊断性差。
- **建议**：把长度与字符集拆成两条独立错误文案（如「标签名过长（最多 255 字符）」）。

### P2-2 `tasks:stop` 与自然结束的竞态：成功任务被记为 `stopped`（未处理）

- **现象**：快捷任务 `console.log(1)` 已输出并退出，但在 `close` 回调完成前调用 `tasks:stop`，最终记录为 `status=stopped` 且 `exitCode=0`（步骤 40）。

- **说明**：这是窄窗口竞态，非稳定复现；本次由脚本连续调用命中。
- **建议**：`stopTask` 前若进程已退出或 `exitCode` 已确定，优先保留 `succeeded/failed`；或在 `stop` 记录里同时保留 `stopRequested` 标记供 UI 区分。

### P2-3 无 remote 的 `fetch` 返回 `success=true` 且提示「Git 操作已完成」（未处理）
